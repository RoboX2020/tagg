## Why a separate migration Worker and no import endpoint on the app

Cloudflare offers no REST API or wrangler command for Durable Object storage, so rows must be written by code running inside Cloudflare.
The app Worker gets no import route. The migration Worker is a separate script bound to the old KV namespace (SRC) and the Store class (STORE). It answers 404 to everything unless MIGRATE_TOKEN is set and sent as a Bearer token (constant-time compare), is deployed only for the window and deleted afterwards. The data never leaves Cloudflare, so the move itself needs no exported plaintext. The secret is created for the move, stored in the vault, and never printed.

## Limits that shape the procedure (Cloudflare docs read 2026-10-31)

- KV Free: 1,000 writes/day, 100,000 reads/day, 1,000 operations per Worker invocation (developers.cloudflare.com/kv/platform/limits).
- Workers Free: 10 ms CPU and 50 subrequests per request (developers.cloudflare.com/workers/platform/limits). The migration Worker therefore uses pages of 50 keys. Raise it only after measuring.
- KV reads are eventually consistent: a change can take up to 60 seconds or more to show in other locations (developers.cloudflare.com/kv/concepts/how-kv-works).
- DO SQLite Free: 5 GB per account, with the per-object cap reached writes fail but reads and deletes still work (developers.cloudflare.com/durable-objects/platform/limits).
- The copy reads KV, which is not capped by the 1,000 writes/day. The rollback replay WRITES KV and is capped.

## Procedure

0. Preconditions: the user approves in their own words. Vault holds the backup key (32 random bytes, generated by the agent into the vault, never shown) and MIGRATE_TOKEN. Rehearsal on a synthetic namespace passed with these exact scripts. KV writes used today are low enough (check the dashboard) because the freeze flag itself is one write.
1. Snapshot A (offline safety copy, before the freeze): list keys (with `expiration`) and bulk-read through the KV REST API, encrypt AES-256-GCM, authenticated header `tagg-backup-v1`, store outside the repo. Record live key count and SHA-256 over sorted key, value and expiry. Stop on any read error.
2. Freeze: write `cfg/freeze` = "on" to KV (1 write). Each Worker isolate caches the flag up to 5 s, and other KV locations can lag 60 s or more. Wait 120 s. Requests already past their last write when the flag flipped finish normally. A request that already started can be mid-way, so the wait is the drain.
3. Drain proof: take snapshot B and snapshot B2 one minute apart (same hash method as A). B and B2 must be identical. If they differ, a writer is still active: keep the freeze, wait, repeat. B is the migration source and differs from A only by writes that landed before the freeze took effect.
4. Deploy the migration Worker (separate script, bound SRC to the old KV namespace and STORE to the Store class, MIGRATE_TOKEN secret). Run /copy page by page, keeping the returned cursor. On any error, resume from the last cursor (copy is idempotent). The expiry is copied as an absolute time (no extension), expired keys are skipped.
5. Verify: run /verify across all pages (0 mismatches required) and /count (must equal the live source count from B). Keep the freeze on if either fails. A failed or partial copy is safe: production still serves from KV, frozen.
6. Deploy the DO worker with `cfg/freeze` still on (the flag was copied). Check with synthetic accounts that existing logins and card reads work. No writes yet.
7. Unfreeze: clear `cfg/freeze` on the new side. Watch error rate and CPU for 30 minutes. Delete the migration Worker and its secret.
8. Rollback rule, decided BEFORE step 7 by counting: rollback replays the keys changed on the new side since the unfreeze into the old KV, which costs one KV write per changed key against the 1,000/day Free cap (and what the day already used). Tested: if the budget runs out the replay stops at the cap, stays resumable, and converges next day with deletes included. While a replay is incomplete the site stays frozen. If changed keys exceed the remaining budget, do not roll back mid-day: either fix forward on the DO build or stay frozen until the budget resets. Rollback steps: freeze the new side, replay changed keys into KV, redeploy deployed-prod 7f01a99, verify counts, clear the KV freeze.
9. The old KV namespace is kept untouched for at least 30 days. Nothing is deleted.

## Downtime

Not estimated as a promise. What is known: the freeze, the 120 s wait, the double snapshot, the page copy (50 keys per call, so a few thousand keys is on the order of 100 sequential calls) and the verify pass all sit inside the window. Real per-call time on Cloudflare has not been measured: do that in the Cloudflare rehearsal first. Reads keep working the whole time; only writes (sign-up, saving a card, connecting, accepting) return "Tagg is being moved to new storage. Try again in a few minutes."

## Remaining blockers

1. The user's cutover decision.
2. A volume rehearsal (thousands of synthetic keys) to measure copy time; the 61-key run only shows about 0.3 to 0.4 s per page of 50. The rehearsal also found that the DO Store must be deployed with the new migration ops BEFORE the migration Worker runs (an older Store silently skipped them); Store now throws on an unknown op and the migration Worker checks result counts.
3. Operator snapshot script (KV REST export, encrypted).
4. Decision on the KV write budget rule above.
5. The existing KV lost-update window and 1,000 writes/day signup cap remain until the cutover.
